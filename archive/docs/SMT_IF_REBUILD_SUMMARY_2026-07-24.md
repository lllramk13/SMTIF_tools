## 4. 最重要的架构发现

### 4.1 游戏不是只有一套文字系统

最初大量误判都来自把不同界面的文字当成同一种格式。现在确认至少有三条主要路径：

| 路径 | 文本格式 | 字库/入口 | 典型用途 |
|---|---|---|---|
| F13 动态文字 | 16 位内部字码，`FFFF` 结尾 | F13；对话/legacy 动态渲染 | 剧情、动态菜单 |
| F14 静态文字 | 16 位内部字码，`FFFF` 结尾 | F14；`0x800475FC` | 固定菜单、名字、技能、选项 |
| 原版小字 UI | 字节串/有限 Shift-JIS | `0x80046D08` | 原版假名、部分系统 UI |

其中第三条并不是完整的“任意 Shift-JIS 汉字渲染器”。Python 能把中文字编码成 Shift-JIS，
不代表游戏的小字纹理里存在对应汉字；不支持的字节会被逐个画成假名或其他错误图块。

### 4.2 游戏内部正文并不是 Shift-JIS

主文本是一串两字节小端内部字码，例如：

```text
字码 字码 字码 ... FF FF
```

控制符同样占两字节，高字节通常为 `FF`。因此正文不能用普通日文编码工具直接替换；码表、字库和
文本必须同步生成。

### 4.3 F13 和 F14 是两种完全不同的资源

- F13 是 1bpp 动态字库，容量 0xACE=2766。
- F14 是 208×252 的 4bpp 四平面静态纹理，容量固定为 0x567=1383。
- F13 的高字码可用，不代表 F14 能显示同一个字。
- “字占着位置但显示空白、黑块或彩色方块”通常是 F14 字码越界，而不是文本位置错了。

## 5. 文本资源管线的重建

### 5.1 找回游戏实际读取的文本副本

一些日文在 F0016 里已有翻译副本，但游戏实际读取的是 F0018 中另一份未翻译副本。
旧工程把 F0018 的危险资源整体 passthrough，导致字库重排后原版日文字码被解释成中文码，
表现为“越玩越乱”。

本轮通过 RAM dump 和原/新码表交叉解码，区分出：

- 原版码表能解成完整日文、新码表解成乱码：实际仍在读原版数据。
- 新码表能解成中文：汉化注入已生效。

最终对 F0018 0x1F5C 使用固定内部布局的原地替换，不再整块放弃。

### 5.2 三层“不能移动”

游戏的数据并不总是只通过指针表读取。现在区分三层稳定性：

1. **光盘文件不能随意变长或移动**：LBA、FILEPOS 和 ISO 记录必须一致。
2. **文件内资源不能随意移动**：部分代码按固定文件偏移读取资源。
3. **资源内字符串不能随意移动**：部分菜单直接读取解压缓冲中的固定偏移。

这解释了为什么“指针表看起来完全正确”仍会卡死。

### 5.3 Exact-size 与扩容固定布局

资源重建现在优先满足：

- 原资源偏移不变。
- 原声明大小不变。
- 压缩内容能完整回环解压。

对于字符串本身也被固定偏移读取的块，使用固定布局：

- 放得下的译文写回原槽。
- 超槽译文在允许时追加到解压缓冲末尾，仅改对应指针。
- 压缩后的资源仍必须放回原文件槽。
- 已确认固定偏移读取的菜单块继续使用短译文，禁止把字符串搬走。

当前 262 个原本会紧凑重排的块改用了扩容固定布局，整盘 750 个处理块不再依赖全块紧凑重排。

### 5.4 PC=0x00020002 卡死的根因

守护灵、获取仲魔、交涉、回复点等看似无关的卡死，实际是同一问题：

1. 紧凑重排改变资源位置。
2. 游戏仍按固定偏移读取跳转表。
3. 读到字码数据并把它当函数指针。
4. `jr` 跳进 RAM 数据区，最终卡在约 `0x00020002`。

修复重点不是“再修一个菜单”，而是恢复资源布局不变量。

## 6. 码表与字库重建

### 6.1 码表必须连续

`codetable.json` 的索引必须从 0 连续到最高码位，不能有空洞。码表重排后，以下内容必须一起重建：

- F13。
- F14。
- 所有正文资源。
- SLPM 内嵌字码文本。
- F0098。
- Overlay 内嵌字码文本。

旧存档和旧即时存档可能保存旧码表下的名字，不能用于新码表版本的可靠测试。

### 6.2 0 号字形必须为空

命名界面把 0 号当空格。连续码表曾在 0 号放入可见字符，造成命名空格显示成别的汉字。

当前规则：

- index 0 固定为全角空格语义。
- `font_builder` 强制把 0 号字模写成全透明。

### 6.3 硬编码字码必须钉住或补丁

游戏并非所有文字都来自字符串，有些指令或表直接存字码。已处理的例子：

- 六维缩写：力、智、魔、体、速、运。
- `知` → `智`。
- `運` → `运`。
- 名字复数后缀 `達` → `等`，即“由美等”。

这些补丁都先校验原字节，再从当前码表解析目标码位，避免下次重排后静默失效。

## 7. F14 容量墙与最终解法

### 7.1 F14 的真实几何

F14 固定为：

- 纹理：208×252。
- 单元：12×12。
- 每平面使用 346 格。
- 四平面合计：`346×4−1 = 1383 = 0x567`。

U/V 表越界后会读到堆中其他数据，因此高码不只是“不显示”，还可能从 VRAM 随机位置取图，
表现为彩色方块、黑块或错位纹理。

### 7.2 为什么不能简单扩容

调查过的扩容结果：

| 方案 | 最小主块大小 |
|---|---:|
| 原几何 | 约 23,489 |
| 17 列 / 357 格每平面 | 23,801 |
| 18 列 | 25,210 |
| 19 列 | 26,600 |
| 21 列 | 29,378 |

F0014 文件总长固定 24,576，主块声明预算 23,541。即使只增加 44 个字位也放不回原槽。

### 7.3 文件重定位也不可接受

`FILEPOS.DAT` 的关键不变量：

- LBA 严格单调递增。
- 文件扇区数与下一项 LBA 差一致。
- 全盘文件基本紧密连续。

把 F0014 单独搬到盘尾会让状态机无法完成读取。全盘后移则要求证明不存在任何硬编码 LBA；
扫描命中与随机对照同量级，无法安全排除漏改。

因此最终决定：

> **F0014 不扩、不移，保持 LBA 2813、24,576 字节。**

### 7.4 上下文别名

关键反转是：1383 个物理格并非都需要全局唯一含义。

原命名键盘长期占用 204 个低码位，而日文键盘名字后来已能通过小字路径显示。于是把确认只走 F14 的
菜单、选项、技能和预设人名记录，在编码时使用“上下文专用低码别名”：

- 普通对话仍用正常 F13 字码。
- 交涉/菜单/技能/预设名在各自记录中使用低码别名。
- F14 对应物理格改画中文字。

当前使用 132 个别名，覆盖 493 个上下文字符；包括：

- `玲` = 0x009E。
- `霆` = 0x00E0。
- `余` = 0x00BD。

test29 的 F14 最小 RLE 主块为 23,489 字节，距离 23,541 的声明上限仍有 52 字节。

### 7.5 名字混合渲染器

直接把所有名字改走 F14 会破坏用户用日文键盘输入的原版名字，因为这些低码位现在被上下文别名复用。

最终在 `0x8004AD6C..0x8004ADF7` 的不可达旧代码尾部放入一个 140 字节 wrapper：

- 如果名字中所有字码都属于原命名字符集，走 `0x80046FEC` 小字路径。
- 只要出现任意非命名码，走 `0x800475FC` F14。

SLPM 2 个名字调用和 overlay 8 个名字调用全部指向这个 wrapper。

结果是：

- 日文键盘输入名字继续使用原版小字形。
- 中文预设名、恶魔名使用 F14。
- 原命名低码位可在受控 F14 上下文中复用。

## 8. Overlay 中发现的遗漏

早期只用 armips 修改 SLPM，无法覆盖运行时加载的代码 overlay。

全盘扫描后发现仍有 8 处 `jal 0x80046FEC`：

- F0048：3 处。
- F0049：1 处。
- F0061：2 处。
- F0091：2 处。

这些调用会把 16 位中文码先转成有限 Shift-JIS，小字纹理找不到中文后显示成点。

`src/overlay_code_patch.py` 现在：

- 校验每个原调用位置。
- 原位把 4 字节 `jal` 改到混合名字渲染器。
- 保持 overlay 文件长度完全不变。
- 验证原小字调用没有残留。

## 9. 第二套 Shift-JIS UI 的发现

### 9.1 为什么一直提取不到

升级界面的：

- `のこりポイント`
- `これでよろしいですか？`

以及加载、无魔法、默认姓名等，并不是普通 16 位字码串，而是 SLPM 中的 NUL 结尾 Shift-JIS
明文。因此原提取器不会找到它们。

关键偏移：

| SLPM 文件偏移 | 原文 |
|---|---|
| 0x0E8E2C | これでよろしいですか？ |
| 0x0E8E44 | のこりポイント |
| 0x0136A4 | ナウローディング |
| 0x0E8C80 | ＮＯ　ＭＡＧＩＣ |
| 0x0EF0A8–0x0EF0D8 | 默认角色名 |

### 9.2 test26：能编码不等于能显示

test26 尝试把中文直接编码成标准 Shift-JIS 写回原槽。实机结果是每个字节被当作独立假名绘制，
两行文字还覆盖到其他区域。

结论：

> `0x80046D08` 只支持原游戏实际准备的有限字符，不是完整 JIS 汉字字库。

test26 的另外 13 条直接汉字替换已全部撤回原文。

### 9.3 test27：只换 jal 仍然不够

两条升级文字改存 16 位内部字码，并把调用从 `0x80046D08` 改为 `0x800475FC` 后，
文字不显示且发生非法内存读写：

```text
Invalid word read/write at 0x78514854
PC 0x80046A1C / 0x80046B44
```

根因是两个渲染器只有寄存器参数兼容，绘制缓冲的栈槽不同：

- 原小字渲染器：`[sp+0x14]`。
- F14：`[sp+0x10]`。

F14 把原 `[sp+0x10]` 的纹理对象当绘制缓冲写，造成内存破坏。

### 9.4 test28/test29：最终升级界面桥接

两处升级调用同时改两条指令：

```text
jal 0x80046D08       → jal 0x800475FC
sw v0,0x14(sp)       → sw v0,0x10(sp)
```

对应文件偏移：

- 0x06DD70 / 0x06DD74。
- 0x06E320 / 0x06E324。

原字符串槽改存 F14 16 位字码，地址和槽长不变。test29 显示：

- `这样可以吗？`
- `剩余点数`

其余直接 Shift-JIS UI 暂时保留原文，必须逐一找到独立调用点和参数约定后再转换。

## 10. 光盘层调查与保留知识

### 10.1 Mode2 Form1 注入

raw BIN 每扇区 2352 字节，用户数据位于偏移 24，长度 2048。

注入器现在会：

1. 按 manifest 找到原 LBA 和文件长度。
2. 只替换用户数据。
3. 重建 EDC。
4. 重建 ECC P/Q。
5. 从镜像回读并逐字节比较。

### 10.2 XA 子头是独立可读性条件

在 F14 搬盘尾实验中发现：

- 普通数据扇区 submode = 0x08。
- 文件末扇区 = 0x89。
- 空白盘尾扇区原本 = 0x00。

即使 EDC/ECC 全部正确，没有 Data 位的扇区仍可能被光驱过滤，读取永不返回。

因此：

> **EDC/ECC 正确不等于 PS1 光驱状态机一定会接受该扇区。**

`src/disc_relocation.py` 虽未启用，但保留了三类昂贵知识：

- FILEPOS.DAT 结构。
- ISO9660 目录记录的 LE+BE 同步修改。
- XA 子头及末扇区 submode。

## 12. 失败实验留下的结论

失败版本不是废时间，它们确定了边界条件：

| 实验 | 结果 | 得到的结论 |
|---|---|---|
| F14 加列扩容 | 压缩后超原槽 | F14 物理容量不能靠小改扩大 |
| F14 单独搬盘尾 | CD 状态机不返回/黑屏 | FILEPOS 顺序和 XA 子头都参与读取 |
| F14 后文件全盘后移 | 无法证明硬编码 LBA 已全部覆盖 | 风险不可接受 |
| 直接换 F14 调用到 F13 动态渲染器 | 生命周期/堆分配模型不同 | 不能把立即绘制简单改成保留对象 |
| test26 中文 Shift-JIS | 中文字节变假名 | 小字渲染器不是完整 JIS 字库 |
| test27 只换 `jal` | 非法内存写 | 必须同时适配栈参数 |
| 资源补零留空隙 | 顺序扫描失败/黑屏 | 固定偏移与顺序读取必须同时满足 |
| 全块紧凑重排 | 菜单错位、跳转卡死 | 指针表正确不代表外部没有固定偏移引用 |

## 14. 当前验证方式

每次正式镜像至少验证：

1. 原版镜像 SHA-256。
2. 原版 SLPM SHA-256。
3. armips 修改字节数和关键 opcode。
4. 所有直接指令补丁的原字节。
5. 所有固定槽的原文和槽长。
6. F13/F14 压缩后能回环解压。
7. F0014 仍为 24,576 字节、LBA 2813。
8. FILEPOS.DAT 保持原版。
9. 替换文件从最终镜像回读后与构建产物一致。
10. 相关扇区 EDC/ECC 正确。
11. `玲`、`霆`、`余` 的 F14 字模与码位一致。
12. `玲子`、`雷霆`、升级两句在最终资源中的字码与计划一致。

## 16. 给后续接手者的硬规则

1. 永远从 `Game/ogd/` 和 `extrac/` 的干净原版构建，不在旧补丁产物上二次打补丁。
2. 改码表后必须全量重建字库、文本、SLPM 和 overlay。
3. 看到某字在 F13 正常，不代表它在 F14 可用；先检查 `<0x567` 和真实字模。
4. 不要把“能编码成 Shift-JIS”误认为“小字渲染器能显示”。
5. 不要只看资源内部指针表；外部代码可能按固定文件偏移或解压偏移读取。
6. 不要扩大或移动 F0014，除非重新证明 FILEPOS、ISO、XA 子头和全部硬编码 LBA。
7. MIPS `jal` 的延迟槽属于调用的一部分；更换渲染器时必须核对寄存器和栈参数。
8. 任何原位补丁都先校验原字节，发现不符立即失败，不要“尽量写进去”。
9. 测试码表变更必须冷启动并优先新游戏，旧存档名字可能使用旧码。
10. 保留失败版本对应的结论，但不要继续使用 test26/test27。

## 17. 最终评价

本轮真正解决的不是某一个乱码或某一个卡死，而是建立了对以下问题的统一解释：

- 游戏从哪里读取文本。
- 文本在文件中怎样压缩和定位。
- 字码如何进入 F13、F14 或小字纹理。
- 为什么某些字正常、某些字空白、某些字变彩块。
- 为什么指针表正确仍会卡死。
- 为什么 EDC/ECC 正确仍可能读盘不返回。
- 为什么同样是“换渲染器”，有时只改 `jal` 就够，有时还会破坏内存。

现在项目已经从“靠历史补丁和现象猜测”进入“可以从干净原盘重复构建，并用地址、字节、字模、
资源布局和镜像回读解释结果”的阶段。剩余工作主要是翻译回填、少量特殊 UI 和全流程 QA。
