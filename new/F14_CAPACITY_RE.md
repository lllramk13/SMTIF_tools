# F14 静态字库容量问题 —— 逆向记录（2026-07-24）

## 结论先行

**F14 的硬上限是 1428 字位，而翻译需要 2469 字。靠 F14 永远修不完"缺字"类 bug。
唯一根治是把静态文本改走 F13 动态字库（容量 0xACE=2766）。**

## 已确诊的 bug 类别（§9.4 #15 的第 4~6 次复发）

| 现象 | 位置 | 缺字数 |
|---|---|---|
| 交涉/行动选项空白 + 彩色方块 | F0076@0x2C7C、F0084@0x800/0xE000 | 89 个字 / 228 条 |
| 皮克希"雷+黑块" | **F0094-00002630 技能名表**（从未加进静态集） | 45 个字 / 49 条 |
| 技能说明缺字 | F0094-00002D98 | 93 条 |
| 战斗消息、恶魔闲聊 | F0075、F0077/F0084 | 上千条 |

皮克希只是运气差：ジオ→落雷（落 0x3AB / 雷 0x41B 都 <0x567，正常）→
**ジオンガ→雷霆，霆 0x855 ≥0x567**。冰系（寒/冻）、核热（末）、辅助（漂浮/摇篮曲）迟早全中招。

## F14 绘制架构（反汇编所得）

```asm
; ---- 初始化 0x80047404 ----
s2 = 346 (0x15A)              ; @0x8004740C  每平面格数
[0x8010B4C0] = 0x567          ; @0x80047430  容量
[0x8010B4C4] = alloc(0x400)   ; 解析后字形缓冲（0x400 = 512 个字码）
[0x8010B4C8] = alloc(容量*4)  ; ★字形 U/V 坐标表
; 循环用 s2 填 U/V：三个平面 346 + 一个平面 345（@0x800474B4 的 s2-1）
;   → 346*3 + 345 = 1383 = 0x567，严丝合缝
; 坐标用 /441(21*21) 与 /21 的除法魔数（0x4A4DC96F / 0x30C30C31）算出

; ---- 绘制 ----
0x800475FC(a0=字符串, a1=x, a2=y, a3=属性标志, [sp+0x10]=arg5)   ; 薄包装
    s0 = [0x8010B4C4]
    jal 0x8004719C(a0=串, a1=s0, a2=1)        ; 解析文本 → 字码数组
    jal 0x80047688(a0=s0, a1=x, a2=y, a3=标志, [sp+0x10..0x1c]=s1,-1,1,0)

0x80047688(真正的绘制)
    a1 = 0x8010B4C0                ; ★F14 描述符是硬编码的，不是参数
    s6 = [0x8010B4C8]              ; U/V 表
    a0 = [[0x80107378] + 0x2448]   ; 纹理句柄，由 a3 的 bit[5:2] 选
```

### 彩色方块的确切成因
U/V 表按 **`容量 × 4` 字节**分配。字码 ≥0x567 → **读到分配区之外的堆内存** →
拿到垃圾 U/V → 从 VRAM 随机位置取图 → **彩色方块 / 黑块**。空白则是取到全透明区域。

### 为什么容量最多只能到 1428
纹理 208×252，12×12 格 → **17 列 × 21 行 = 357 格/平面**，4 平面 = **1428**。
代码里的 441(=21×21) 魔数说明**引擎本身支持 21 列**，但纹理只有 17 列。
要用满 441 需把纹理做成 252 宽 = 31752 字节原始数据，
而 **F0014.BIN 是固定 24576 字节**（当前 23541+1035 已 100% 填满，光盘注入不允许改变文件长度）→ 装不下。

## 已排除的方案

- **B（放大 F14 纹理）**：被 F0014.BIN 固定文件大小堵死。
- **①（346→357，+44 格）**：技术可行（改 `0x8004740C` 的 s2、`0x80047430`/`0x80078268` 的 0x567、
  以及打包器 `GLYPHS_PER_PLANE`/`STATIC_GLYPH_COUNT`/`ORIGINAL_MAX_GLYPH_INDEX`，三者必须严格同步，
  改错=整个静态字库全废）。但只换来 44 格：技能名要 45（差 1），选项要 89。**不值得，风险预算留给 C。**
- **改词**：约一半的缺字（咬/爪/触/罚/吻/九/呼叫伴/呐喊/狱/獠/冥/菩/奢/右/休/振翅/横/压/截）
  连同义替代字**也不在 F14 里**，无解。

## C 方案（进行中）

把静态文本绘制改走 **legacy 动态渲染器 `0x800495B0`**（F13，容量 0xACE=2766）。

**不能直接换 `jal`** —— 两者调用约定不同：

| | `0x800475FC` (F14) | `0x800495B0` (动态) |
|---|---|---|
| 栈帧 | `sp -= 0x38` | `sp -= 0x48` |
| 字库对象 | `[0x8010B4C4]` | `[0x8010B4D8]` |
| 寄存器参 | a1→s2, a2→s3, a3→s4 | **a0→s2, a1→a0, a2→fp** |
| 栈参 | 1 个 `[sp+0x10]` | **3 个** `[sp+0x10/0x14/0x18]`，a3 另存 `[sp+0x0C]` |

### ★ C 的致命障碍（2026-07-24 确认）：两者渲染模型不同

反汇编 `0x800495B0` 主体后发现，它**不是立即模式绘制**，而是**保留模式的文本对象系统**：

```asm
0x800495B0(a0=宿主对象, a1=字符串, a2=xy打包(低半x/高半y), a3=?, [+0x10],[+0x14],[+0x18])
    s4 = [0x8010B4D8]                    ; 动态字库对象
    a0 = a1                              ; ★字符串是第2个参数，不是第1个
    jal 0x80049300(a0=串, a1=s4, a2=1)   ; 与 F14 的 0x8004719C 完全对称
    ...
    jal 0x8008B3DC(a0=s2=宿主, ...)       ; 注册进某个列表
    jal 0x8002C6A8(a0=0x154, ...)        ; ★每次调用 malloc 0x154 字节
    sw s3,0x24(t0)                       ; ★把新节点挂入链表
    [s3+4]=[+0x14], [s3+8]=x, [s3+0xA]=y ; 填节点字段
```

而 `0x8002C6A8` 经查是 **debug 版 malloc**（`0x800EB290` 真分配 + 把 size/文件名/行号
记到 `gp+0x6EC/0x6F0/0x6F4`；调用处 a1 是文件名字符串指针、a2 是行号）——**是真堆分配，
不是每帧重置的 arena**。

⇒ **把立即模式的 F14 调用重定向到它，会每次绘制泄漏 340 字节 → 堆耗尽 → 崩溃。
简单 shim 方案不可行。** 要用动态路径必须按"创建/销毁文本对象"的生命周期改写调用方，
属于**逐屏移植**，每个屏幕都是独立的 RE 工作量。

## ★★ 采用方案：加宽 F14 纹理 + 文件挪到光盘末尾（2026-07-24 全部前提已验证）

用户提出"把 F14 挪到 disc 末尾"，顺此发现引擎本来就支持更大的字库。

### 关键发现：U/V 表结构（`0x800474E0` 循环解出）
每项 4 字节 `{U, V, 页号, 平面号}`：
```
a1 = 字号 / 441 → 页号（★引擎原生支持多纹理页，441 溢出自动进位）
a1 = 字号 % 441 → 页内序号
列 = 页内序号 / 21 → U = 列*12
行 = 页内序号 % 21 → V = 行*12
```
**441 = 21×21 = 一个 PS1 纹理页(256×256)在 12px 格下的最大格数。**
原版纹理只做了 208 宽（17 列），每平面 346 → 容量 1383，**引擎设计上限根本没用满**。

### 验证过的三个前提
1. **VRAM 有空间**（用 test19 的 `ram_vram/F14U.bin` 精确匹配）：
   F14 在 **VRAM x=576, y=256，占 52×252 单元，正好在纹理页边界上（576=9×64）**。
   页内右侧 **12 个单元 × 252 行全空**（非空行数 0/252）→ 扩到 63 单元（252px）刚好用满这一页，
   不碰任何其它图。（纵向只剩 4 行，加不了新行 → **加列不加行**。）
2. **光盘有空间**：末尾 **150 个扇区确认全零**；新文件 30350 字节 = 15 扇区（原 12）。
3. **游戏用自己的文件表**：`FILEPOS.DAT`（LBA=23, 848 字节）= `{u32 LBA, u32 size}` 数组，
   **偏移 112 = F0014 的 LBA(2813)，偏移 116 = 大小(24576)** → 改这 8 字节即可重定位。

### 实测数字
| | 原 | 新 |
|---|---|---|
| 纹理 | 208×252 | 252×252 |
| 每平面 | 346 | 441 |
| 容量 | 1383 (0x567) | **1764 (0x6E4)** |
| raw | 26208 | 31752 |
| 压缩后文件 | 24576 | 30350（15 扇区）|
| 最大 U | 204 | 252 ≤ 252 ✅ |

静态集需求 1154 + 89(选项) + 45(技能名) = 1288 → **富余 476 格，不用改任何译文**。

### ★ 黑屏踩坑：XA 子头（test20/21/22 全黑屏的真因）
前三版黑屏，二分（bisectA = 原几何 + 仅重定位）也黑屏 ⇒ 问题在**重定位本身**。
根因是 **CD-ROM XA 子头**（sector 偏移 16..24，`[file,channel,submode,coding]` 存两份）：

| 扇区 | submode |
|---|---|
| 正常数据扇区 | **0x08**（bit3=Data） |
| 文件最后一个扇区 | **0x89**（EOF\|Data\|EOR） |
| 光盘末尾空白扇区 | **0x00** ← 数据位没置 |

PS1 的 CD 控制器按 submode 过滤扇区，没有 Data 位的扇区不会进数据 FIFO → 读操作永不返回 →
挂死黑屏。**EDC/ECC 全部有效，所以常规扇区校验发现不了。**
修法：`disc_relocation.write_relocations` 写入时改写子头，并在回读时断言。

（同期排除的错误猜测：ISO 目录未同步 → 已补但不是主因；CLUT 4 字节对齐 → 实测原本就对齐，
test23 与 test21 逐字节相同；PVD 卷空间 → 109021 扇区，新位置在卷内。）

## 现实可选路径（已被上面的方案取代，保留作背景）

1. **+44 格（346→357）**：技术已摸清，但只够技能名（差 1 个），选项仍缺 45。
2. **系统性改词**：让静态屏文本（物品名/技能名/交涉选项）**共用一个 ≤1383 字的字符集**。
   零技术风险，是引擎约束下的常规做法，但需要翻译组配合。
3. **逐屏移植到保留模式动态渲染器**：能力上限最高，但每屏都要处理文本对象生命周期，工作量大。
4. **1+2 组合**：先拿 +44 格，再对剩余缺字改词。
