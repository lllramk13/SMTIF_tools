目标:在 SCE「Research and Development 1」LOGO 之后、开场动画之前,插入一屏汉化组水印。

**状态:未完成。** 显示侧已完全打通,卡在读盘的容量/时序约束上。本文记录已查实的机制、每一次尝试的结果、以及推翻过的错误结论,供下次接手用。

代码保留在 `new/src/CN.asm` 的 `boot_screen_*` 段,所有挂钩已注释掉(`DISABLED` 横幅),留作死代码不影响构建。

## 1. 开机画面是什么

| 文件 | 内容 | 规格 |
|---|---|---|
| `D/F0093.BIN` | SCE「Research and Development 1」LOGO | 320×240 8bpp,10,240 字节 |
| `D/F0083.BIN` | 免责声明「このゲームは フィクションであり…」**已汉化** | 同上,中文版 RLE 后 7,174 |

播放顺序:**R&D → 免责声明 → 开场动画(F0099)**。

F0093 由 `0x8002C794` 绘制;F0083 走**另一条显示路径**(VRAM 布局不同),那条路径尚未定位。

### 定位方法(跨游戏通用)

`new/tools/locate_vram_source.py`:VRAM dump + 光盘镜像 → 直接报出屏幕上的东西来自哪个文件,不需要任何格式知识。

原理:RLE 只在重复字节上省空间,**高熵区段(抗锯齿文字、渐变、细节)被原样写成字面量**。工具按"字节种类数"挑样本、故意跳过平坦区。一条穿过 "Research and Development" 字母的 48 字节样本一击命中 F0093 —— 而穿过背景的样本全部落空。

## 2. 图像格式

`02 01` RLE 块。**头里的 `width_words` 是 16 位 VRAM 字数**,`graphic_resource` 按 4bpp 算 `pixel_width = width_words * 4`,但开机屏是 **8bpp**,真实宽度是 `width_words * 2`。

**一个文件 = 两个块**:图像块 + 尾部 `256×1` 的 CLUT 块,块间 **4 字节对齐**。重编码后大小变了,CLUT 必须跟着搬 —— 否则整屏颜色错乱。`boot_screen.py` 早期版本就踩过这个坑。

**块头第 8..12 字节 = 该块的 VRAM 目标坐标**:

| | 图像目标 | CLUT 目标 |
|---|---|---|
| F0093 | 字 (320, 0) | (0, 480) |
| F0083 | 字 (0, 0) | (0, 0) |

`0x8002C794` 的贴图/调色板坐标**写死按 F0093 的布局**。任何要走这条路径的图必须用 `--dest-from F0093` 套坐标。**不要改 F0083 的坐标** —— 改了它自己那条路径就画崩(test4 亲测)。

**调色板不是线性的**,也不在块头里。F0093:索引 255 = 黑、0 = 近白。F0083:31 = 黑底、1 = 纯白墨色。可从"帧缓冲像素 ↔ 索引"反解出完整 CLUT(R&D 屏的 FB 原点正好是 VRAM (0,0))。

工具:`new/tools/boot_screen.py` export/import,未改动的 PNG 往返**逐字节相同**(已验证)。注意 `compress_rle()` 返回带 12 字节头的完整资源,图形块要的是 `[12:]` 裸流。

## 3. 显示例程

`0x8002C794`,全 SLPM **只有一个调用者 `0x8002BF64`**:

```
建立 320×240 显示
读 5 扇区(LBA 来自 0x8002C82C 的 lw a0,0x7a28(a0) = FILEPOS[93])
等待完成 (0x800287B4)
两个精灵绘制 (0x8002CA9C ×2)
淡入 → 停 0x78 = 120 帧(按键可跳)→ 淡出
收尾 (0x800E2604)
```

参数块在 `0x800EB7C4`:`{u16 arg1=0, u16 lba偏移=0, u16 扇区数=5, u16 arg4=2}`。

精灵参数:`0x8002CA9C(a0=结构体, a1=x, a2=y, a3=宽, [sp+0x10]=高, [sp+0x14]=纹理页)`,写进结构体偏移 `0x0C`。图分两个精灵画:**纹理页 5**(VRAM 字 320,256 texel 宽)+ **纹理页 7**(字 448,64 texel 宽)。

**寄存器**:`s0` 在 `0x8002C7FC` 设为 0xF0(精灵高度),`0x8002C924` 淡出时覆盖成指针;`s1` 是淡入淡出计数器,结束时为负;`s2` 头部设定后不再被写;`s3` 在 `0x8002C810` 重算。**`s4..s7` 全程未被触碰**(逐条扫过)。

## 4. 插页的四处补丁

自由空间 `0x800FE260`(160 字节,夹在两张数据表之间,无任何引用)。巧合:`0x80100000 - 0x1DA0` 正好等于它,所以 `0x8002C818` 的 `lui a0,0x8010` 一个字节都不用动。

| 地址 | 改动 |
|---|---|
| `0x8002BF64` | `jal boot_screen_start` —— 设 LBA + 页号,尾跳进例程 |
| `0x8002C82C` | `lw a0,0x7a28(a0)` → `lw a0,-0x1DA0(a0)`,图片来源改成变量 |
| `0x8002C954` | 收尾调用 → `boot_screen_next` 页面调度器 |
| `0x8002C860` / `0x8002C888` | 纹理页立即数 5/7 → `addu v0,zero,s4` / `s5` |

**不能直接调两次 `0x8002C794`**:它的函数头会重跑 `0x800E2604` / `0x800E2320`(图形+回调复位),第二次调用把刚建好的东西拆掉 → VSync 失效(LOGO 快闪而非停 2 秒)→ CD 等待永远等不到中断。正解是**内部循环**。

**重入必须恢复 `s0` 和 `s1`**。只恢复 `s1` 的那一版:图只画出上面一部分,越界后触发 BIOS `SystemErrorUnresolvedException`(pc=0xA0, $t1=0x40)。**截断和死机是同一个 bug。**

## 5. 读盘的两条路径

```
平时加载文件  load_file(0x80029074) → 0x8002904C → 0x80028FF0 → 0x80028F64 → 状态 10
开机屏例程                            0x800291DC → 0x80029144 → 0x800290B0 → 状态 12
```

两个启动器**代码几乎逐条相同**,都发同一条命令(`0x800CAD78`,a0=0xA0,a2=6=CdlReadN,回调 `0x80028328`),**只差记录的状态号**。

但 Complete 中断处理器 `0x80028328` 的分发表在 `0x8001000C`(索引 = 状态 - 2,只覆盖 2..12):

```
状态 10 → 0x8002839C → 推进到 11
状态 12 → 0x8002839C → 推进到 13
```

**状态 13 那条分支只需要工作一次。**

诊断值:`[0x800EB71C]` = CD 状态(`0x01` 空闲 / `0x0D` 卡死),`[0x80107730]` = 忙标志,`[0x801076D8]` = 重试计数(卡死时 `0x0F` = 用尽),`[0x801076DC]` = 剩余扇区,`[0x8010772C]` = 当前 LBA。

### 缓冲区布局(这是最后的硬约束)

```
0x801DF000   ← 扇区读取目标
0x801E2800   ← 下一个结构,相距 0x3800 = 14,336 字节 = 7 扇区
0x801E4000   ← 再下一个
```

**单次读最多 7 个扇区。** 设 10 个会冲垮 `0x801E2800` / `0x801E4000` 两个 CD 驱动结构 —— 两页都画完了才黑屏,而且没有异常,因为被破坏的是驱动数据不是代码。

## 6. 尝试记录

| # | 做法 | 结果 |
|---|---|---|
| 1 | 直接调两次 `0x8002C794` | LOGO 快闪、CD 等待卡死(图形/回调被重复复位) |
| 2 | 内部循环,恢复 `s1` | 图截断 + BIOS 异常(漏了 `s0`) |
| 3 | + 恢复 `s0` | **两页正常显示**,之后黑屏 |
| 4 | 读盘改走 `jal 0x8002904C` | 驱动健康但两页都不显示(两条路径参数含义不同) |
| 5 | 页面挪到盘尾空扇区 108871 | 黑屏 |
| 6 | + 整段空区盖成数据扇区(submode 08) | 黑屏 |
| 7 | 页面挪到 `ZZZ.BIN` 开头 95371 | 黑屏 |
| 8 | 第二页读**同一个 LBA** | **正常** —— 无需寻道 |
| 9 | 第二页读 LBA 8977(仅差 5 扇区) | 黑屏 —— **距离无关,是"要不要寻道"** |
| 10 | 启动器改 `jal 0x80028F64`(记状态 10) | 崩到异常向量 `0x80000080`,第一屏就不显示 |
| 11 | 一次读 10 扇区、两张图、纹理页切换 | **两页正常显示**,之后黑屏(缓冲区溢出) |
| 12 | 单次 5 扇区、只画第一页、LBA 95371 | **正常进游戏** —— 确认位置无罪,是扇区数 |
| 13 | 一次读 7 扇区、两张图、水印量化到 2 级 | 第二页显示为纯白,之后黑屏 |

### 已推翻的错误结论(别再走)

- ~~盘尾空扇区 submode 0x00 导致光驱跳过~~ —— submode 确实要改(空扇区是 `0x00`,数据扇区 `0x08`、文件末 `0x89`),但**不是这个故障的原因**
- ~~寻道距离太远~~ —— 只差 5 个扇区照样挂
- ~~显存不够~~ —— 两张图目标坐标不同,各占 160×240 字,VRAM 1MB 绰绰有余
- ~~缓冲区没被溢出~~ —— 早期只看了正常状态下 `0x801E5000..0x801E7800` 全零就排除了,**错在没查那之后还有结构**

### 方法上的教训

- **纯白测试图是个坏选择** —— "图加载成功"和"VRAM 空白"在屏幕上一模一样,导致把两种不同故障混成一个,并据此得出过一次错误的"已修复"结论。诊断图必须一眼可辨
- **拿 A 版本的 savestate 去分析 B 版本的故障** 会得出完全错误的因果链
- DuckStation savestate 取证是这轮唯一稳定有效的手段,见下

## 7. savestate 取证步骤

`.sav` 头部:`0xCC` = 压缩长度,`0xD0` = 解压长度,`0xD4` = 偏移,**zstd** 流。

```python
b = open(sav,'rb').read()
comp, unc, off = struct.unpack_from('<I',b,0xCC)[0], struct.unpack_from('<I',b,0xD0)[0], struct.unpack_from('<I',b,0xD4)[0]
open('s.zst','wb').write(b[off:off+comp])          # 再用 zstd -d 解开
```

解压后:
- **RAM 基址** —— 搜 `FILEPOS[0]` 的签名 `struct.pack('<IIII', 557, 11832, 563, 16756)`,减去 `0x107740`
- **寄存器块在偏移 `0x3E`**,按 4 字节读但整体**错位 2 字节**;顺序是 32 个 GPR + hi + lo + pc
- **VRAM** 紧跟在 RAM 之后(`ram_base + 0x200000`),1024×512 的 16bpp

## 8. 下一步的方向

当前设计只差最后一步:7 扇区的读能装下 R&D(8,912 + 528 调色板)+ 一张 4,880 字节以内的水印,**而 2 级量化的水印实测 4,289 字节是装得下的** —— 但实机上第二页显示为纯白,说明第二个图像块**没有被上传**,块解析器很可能在第一个 CLUT 块之后就停了。

值得先查的:

1. **块解析器在哪、以什么条件停止** —— 找到读取完成后遍历块的代码,确认它是"读到无效类型就停"还是"按总长度走"。若是前者,可能需要把两张图各自带一份完整的 [图像+CLUT] 结构
2. **纹理页 Y 位编码** —— 第二页用了 `0x10|5` / `0x10|7` 表示 VRAM (320, 256)。如果 `0x0C` 那个半字不是标准 tpage 编码,Y 位可能无效,导致第二页采样到了空白显存(**这同样能解释"纯白"**)。可以先把第二张图放在 y=0 的另一段 X(如字 640,纹理页 10/12)来排除 Y 位问题
3. **F0083 那条显示路径** —— 至今未定位。如果找到它,把水印做成"第三条路径"可能比改 R&D 这条更省事

### 成本更低的替代方案

**把水印做进免责声明那一屏(`D/F0083.BIN`)。** 位置一样在 R&D 之后、开场动画之前,零代码改动、零风险,那一屏已经汉化且还剩 3,066 字节空间:

```bash
python tools/boot_screen.py import F0083 --png <图.png> --dest-from-nothing
```

(注意:给 F0083 自己那条路径用时**不要**加 `--dest-from`,坐标必须保持原样。)
