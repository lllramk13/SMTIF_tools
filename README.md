# 《真·女神转生 If...》PS1 简体中文化

PS1《真・女神転生 if…》(SLPM-87154) 的汉化工程。从**干净原盘**一键重建整张光盘镜像，
每一步都带构建期断言。

```powershell
Set-Location 'P:\ROMHacking\SMT IF\new'
$env:PYTHONPATH = '.;vendor'

# 只构建并验证资产，不生成 256 MB 镜像（改任何东西后先跑这个）
python build.py --dry-run

# 生成完整镜像
python build.py --output '..\Game\modified\SMT_IF_CN_xxx.bin' --force
```

依赖：Python 3 + Pillow。

统一码位布局（原 `--unified-normal-text`）现在**默认开启**，是唯一支持的构建路径；
`--no-unified-normal-text` 只作诊断用，绝不能用来出发布镜像。

**每次构建都要确认这三行出现**，缺任何一行说明嵌入文本没注入：

```
F14 context aliases: 22 aliases for 694 characters
Embedded SLPM text: 388/388 translated
Direct UI -> F14: 2 fixed-size strings and renderer calls patched
Changed bytes: 9997
```

> **按键推进对话卡死 / 动态字库失效指针（2026-08-03）**：Mammon 战前对话
> `F0016@0x38990` 的首句比原槽长 4 字节。通用 allow-growth 策略曾把它单独
> 搬到资源尾部 `0x656`，但下一句仍在 `0x66`；首屏通过指针能正常显示，按键
> 推进后却会沿断开的记录布局读入堆数据，把 `0xB370/0xC2C0` 当字码，最终在
> `0x8005BCEC/0x8005BD0C` 解引用 `0xFFFFxxxx` 的假节点。普通对话块现在超槽
> 时统一紧凑重排，只有明确按固定偏移独立查表的 F0017/F0094 四块允许单条
> 外移。`tools/audit_text_resource_layout.py` 会扫描全盘并输出布局策略报告。

> **MARKER 根因与 test64 修复（2026-07-26）**：test62 将错误地址
> `0x7806DC78` 解码为 `$ra=0x8006DC78`，确认最终坏指针读取来自
> `0x8006DC70`。离线图元证明更早的类型 6 F14 绘制才是破坏者：
> 六字符 `NODATA` 的前景+阴影实际需要每行 `0x100` 字节，MARKER 构造器
> 却只分配 `0xD0`，第四行溢出并把对象 `+0x18` 标题指针覆盖成
> `0x7811B424`。test63 误补了未触发的同型调用 `0x80084E94`；真实对象
> 字段证明它走公共构造器的另一条自动估算路径。test64 最初在分配前的公共点
> `0x8006F0A8` 把所有类型 6 且小于 `0x100` 的行跨度一律提升，后来证明这会
> 误伤 EQUIP 的合法小跨度对象。test77 将条件收窄为 MARKER 的精确特征：
> 仅当类型为 6 且行跨度恰好为 `0xD0` 时改成 `0x100`。
> 诊断护栏和 test61 的堆内日志均已移除。
> test65 另将此前漏掉的 SLPM 静态字符串 `0xE487E`（`ＮＯＤＡＴＡ`）
> 注入为“无数据”，消除 MARKER 空槽位的乱码。
>
> **绿色目标框 / 使用道具与治疗停滞（test66）**：SLPM 的 35 条动作结果消息
> 都以 `{大停顿}`（`FF92`）紧接 `FFFF` 收尾。固定槽通用填充曾把透明 `0000`
> 放在终止符前，实际变成 `FF92 0000… FFFF`，导致动作消息状态机在停顿后
> 继续处理假字符，绿色目标框迟迟不退出。`slpm_text.py` 现仅对
> `0xE6A26–0xE6D57` 的这组指针寻址消息保留 `FF92 FFFF` 相邻，并把未用字节
> 填在终止符之后；列表类字符串仍保持原来的槽尾单终止符规则。
>
> **绿色框后游戏极慢（test67 失败，test68 局部修正）**：
> `杰克霜精技能.bin` 证明消息对象和字形缓存均已正常结束，实际停滞来自 GPU
> DMA 链自环。F14 的阴影复制循环只把 GPU 命令 `0x64` 识别为 20 字节 SPRT，
> 而由原小字路径继承来的半透明图元使用 `0x66`；进入阴影复制后，tag 与包长
> 不一致并破坏 DMA 链。test67 把全游戏的 `0x66` 都改为完整阴影复制，测试
> 证明范围过宽，会使多处卡死或显示错乱，现已完全撤回。
>
> 原小字渲染器本来只产生一遍图元。test68 只在混合 wrapper 的中文 F14 分支
> 延迟槽 `0x8004ADEC` 设置模式 bit 0，关闭这条重定向路径额外增加的 F14 阴影；
> 半透明属性保留，其他原生 F14 调用完全不变。相对 test66 可执行文件只有这一
> 条指令、3 个字节不同。
>
> **升级界面（test69）**：test68 漏掉了另外两处直接由小字改到 F14 的固定 UI
> 调用（`0x8007D570`、`0x8007DB20`）。“这样可以吗？”和“剩余点数”的调用方
> 仍按原小字单遍图元预留固定缓冲，F14 双遍会把相邻文本指针覆盖为
> `0x04xxxxxx` GPU tag；日志 `pc=0x80046984, address=0x041296BC` 与此完全
> 一致。test69 将这两处调用改到 `0x8005C2C8` 单遍适配器。现在所有从小字
> 改道 F14 的入口都保持原来的单遍容量，原生 F14 调用不变。
>
> **角色/恶魔技能界面（test70）**：同时比较 test66 的
> `杰克霜精技能.bin` 与 test69 的 `toumeibroken.bin` 后，发现关闭所有重定向
> 入口的阴影仍不够；原生 F14 技能列表也会产生半透明 `0x66` SPRT，并进入只
> 支持 `0x64` 的阴影复制遍。两份 RAM 的双缓冲都在相差固定 `0x1800` 的对应
> 位置形成相同单节点 DMA 自环，排除了具体角色、恶魔、技能和存档数据。
> test70 在 `0x80047C94` 将非 `0x64` 包送到分类器：`0x66` 只推进源包、不提交
> 多余暗色副本；真正的 8 字节 GPU 状态包仍走原复制路径。test67 的“完整复制
> `0x66`”方案没有恢复。
>
> **绿色动作消息缺字（test71）**：`0xE6A26–0xE6D57` 的 36 条动作结果消息
> 虽在数据表中标为 dynamic，运行时绿色框实际由容量仅 `0x567` 的 F14 绘制。
> 此前它们按完整 F13 码表编码，至少“谁、咏、唱、素、痊、守、张、从、烂”
> 使用了 F14 范围外字码。构建现把这 36 条消息纳入 F14 上下文别名计划，并且
> 只在该地址范围编码时使用低码别名；普通剧情文本不受影响。最终 93 个可见字
> 的最高码位为 `0x552`，139/204 个姓名保留格已使用。构建同时断言 35 条
> `{大停顿}` 消息继续保持 `FF92 FFFF` 相邻。
>
> **全部技能/道具绿框说明（test72）**：test71 只覆盖动作结果消息，未覆盖
> 选择技能或道具时右上角的绿色说明框。截图反查证明这批说明完整位于
> `F0094-00002070`（道具/通用魔法）和 `F0094-00002D98`（角色/恶魔技能）
> 两个块，共 207 条。它们此前同样未进入 F14 别名计划，因而会整句消失，只剩
> 数字“4”等本来就在低码区的字符。test72 将两个完整块加入上下文编码；207 条
> 说明共用 309 个字形，最高码位 `0x55E`，全部低于 `0x567`。当前别名用量
> 180/204，尚余 24 格。
>
> **漏翻 UI、动作插入名与赌场兑换（test73）**：补入此前落在已知表边界之外的
> SLPM `0xE6014`（“使用ＣＯＭＰ”）和 `0xE48A0`（“玄关前”）。F0098
> `0x0906–0x0BFA` 是动作消息通过 `{魔法}` 插入的另一套技能/动作名，和
> F0094 技能列表不是同一份；现补齐 59 条固定槽，并使用与动作消息相同的 F14
> 上下文编码。F0051/F0052 两份赌场兑换 overlay 各补 8 条原位文本。
>
> **test74 字库回退**：test73 曾把队伍预设名“玲子”加入全局 F14 集合并重新
> 排列整张码表，导致已经正常的姓名、状态页和部分固定槽再次错位。test74 撤销
> 这项全局约束并恢复 test72 的码表；构建后 F0013/F0014 与 test72 逐字节相同，
> 但上述漏翻文本仍全部保留。F0098 `ガーディアン実体化` 不是状态页标题来源，
> 状态页的日文标签仍需另行定位。当前别名 180/204，尚余 24 格。
>
> **姓名与 ＮＯＤＡＴＡ 的两条独立成因（test83 / test84）**
>
> 1. **共享大字渲染器没设闸**。`0x800475FC` 只是"强制选 F14"的封装（SLPM 仅 3 处
>    调用）；真正的共享入口是 `0x80047688`，它用 `(a3 >> 3) & 0x3C` 从字体表
>    `0x8010B4C0` 选字库，SLPM 有 24 处调用、另有 8 个 overlay 也在调。状态页顶栏
>    和存档槽姓名都走这里，所以只改 `0x800475FC` 的调用点毫无效果。
>    test83 把分流下沉到 `0x80047688` 入口本身：只由原版命名码组成的串走小字库，
>    其余原样继续。补丁空间用 `0x80047DBC` 那 592 字节——它是 F14 渲染器的第二份
>    编译产物，全库零 branch/jump/指针引用。两个渲染器都读调用方 `sp+0x10`
>    （`0x80047688` 是 −72 帧读 `88(sp)`，`0x80046FEC` 是 −112 帧读 `128(sp)`），
>    两条出口都不需要改栈。
>
>    判断这样做安全的依据：`GUARDIAN` / `NORMAL ITEM` / `EMPTY` / `FILE n` 里都含
>    Ｎ、Ｏ 或 Ｔ 却全部显示正常，说明拉丁标签根本不经 F14；凡是经 F14 且全由原版
>    码组成的串，只可能是姓名或 ＮＯＤＡＴＡ。
>
> 2. **存档列表的 ＮＯＤＡＴＡ 是漏提取，不是渲染问题**。存档槽由 `0x8004800C`
>    绘制——2768 字节的对象方法，**内联逐字排版**（`lw v0,0x38(s1)` 取串、
>    `lhu a0,0(v1)` 取码、`0x800F2910` 查宽度、`0x8010B4C0` 选字库，越界时
>    `j 0x8004844C` 原地死循环），没有可分流的渲染器调用，闸门对它无效。
>
>    但 `ＮＯ　ＤＡＴＡ` 在 SLPM 里有两份：`0x0E64CC`（dynamic，有记录，一直正常）
>    和 `0x0E6E20`（static，**提取时漏掉**）。漏掉的那份保留原版码 `0x41/0x42/0x47`，
>    正好撞上别名 菩/濒/突。补上记录后它被我们的码表重新编码
>    （Ｎ=`0x033E` Ｏ=`0x01FF` Ｄ=`0x011B` Ａ=`0x01F6` Ｔ=`0x0345`，全部 < `0x567`），
>    外观保持 `ＮＯ　ＤＡＴＡ` 不变。旁边的 `ＥＲＲＯＲ　ＤＡＴＡ`（`0x0E6E32`）有记录，
>    所以一直没出问题——这正是判据。
>
> **大字姓名与别名机制是硬冲突**：F14 低码区需要 1174 格、可用 1172，已经超载 2 格，
> 别名（182 格：假名区 161 + ASCII 区 21）是硬需求。原版命名码的姓名要么走小字库，
> 要么放弃等量的别名。当前选择是保留别名、姓名统一走小字库。
>
> **召唤刻耳柏洛斯卡死（test88 实测消失）**：测试组的 `召唤卡死.bin` 证明他们
> 当时那一版 `0x8004844C` 仍是原始自旋、`0x8006F0A8` 也没有 Codex 的 MARKER
> 行跨度修复。异常向量 `0x80000080` 完好，排除 RAM 写穿那一类。
> 召唤列表与存档列表共用 `0x8004800C` 这个通用列表控件，所以「越界字码 →
> `j 0x8004844C` 原地死循环」同时解释了召唤卡死和嫉妒界/贪欲界存档卡死。
> test88 换成跳过该字后实测不再复现。
>
> 注意：该轮测试同时更换了版本与存档，严格说无法断定是哪一项生效；上述是
> 最符合证据的解释。
>
> **DuckStation savestate 可以直接解析**：`DUCC` v50，RAM 未压缩。以
> `saves/耳柏洛斯死机/SLPM-87154_2.sav` 为例，用构建产物 SLPM 的前 64 字节
> 在文件里搜到 RAM 基址（该例 `0x11B4D`），再用栈指针特征值
> （`0x807Fxxxx`）定位 GPR 块（该例 `0x1012E`），其后依次是 hi/lo/pc/npc。
> **卡死时存的 savestate 比 RAM dump 更有用**，因为能直接读到 PC。
> 状态里记死了光盘绝对路径，换机器要么复刻路径、要么先跑游戏再从文件读状态。
>
> **译文丢失停顿控制符导致对话被刷掉（test86）**：`▽`（`01FF`）是等待按键、
> `{大停顿}`（`92FF`）是长停顿。译文一旦丢掉它，脚本不会停——对话瞬间刷过去
> 并径直执行后面的指令，实机表现是"自动走出房间"。测试报的"把软盘交给电脑室
> 同学后问进度"和"占卜馆选择不占卜"正是这一类。
>
> 全表比对 13125 条已翻译记录后共查出 **29 条**丢失（`text.json` 28 条 +
> `slpm_text.json` 1 条），按 `※※※※※※※` 分段对齐逐段补回，落位精确到
> 原文该符所在的那一段。`overlay_text.json` / `f0098_text.json` 无丢失
> （比对时要先把原文的原始记法 `{FF01}`/`{FF92}` 归一化成 `▽`/`{大停顿}`）。
>
> `F0018-00001F5C-000006DE` 是固定槽，补 `▽` 后超 2 字节；三条重复记录里
> `
` 之前的行尾空格不产生任何视觉效果，去掉即可。
>
> **`src/control_code_audit.py` 现在是构建期断言**：译文丢失停顿符直接构建
> 失败。只查"丢失"不查"新增"——中文换屏时译者主动加 `▽` 是合理的。
>
> **存档界面卡死与合体相性表图例（test85）**
>
> 1. **存档卡死是原版的 assert 自旋**。`0x8004800C` 的内联排版循环里：
>    `slt a0,a0,v1`（字码 < 字库格数）不成立就落到 `8004844C: j 0x8004844C`
>    —— 原地死循环，永不退出。所以存档槽字符串里**只要出现一个 ≥ `0x567`
>    的字码就永久卡死**，这正是嫉妒界/贪欲界（以及后面所有地名越界的区域）
>    的现象。现改成 `j 0x80048974`——那是循环自己的“下一个字符”点，
>    此时 `s2`（图元指针）和 `s5`（x 游标）都还没推进，跳过即可，无需回滚。
>    越界的串现在只丢一个字，缺口位置正好指出是哪条串需要修。
>
> 2. **合体相性表图例是整块漏翻**。`overlay_text.json` 原本只覆盖
>    `F0049 / F0092 / F0051 / F0052`，**`F0048` 完全不在注入范围内**，
>    图例块 `F0048 0x9240–0x92BC` 保留原版日文码，被重排后的字库画成
>    「训肩什魔」这类乱码。
>
>    定位方法值得记下来：`PreWork/if备案/原始码表.txt`（UTF-16，1383 条
>    `码位=字`）是原版日文码表。把屏幕上的乱码字反查我们码表得到码位，再查原始
>    码表，就能还原原文——`训肩什魔 → 通常悪魔`、`置体恰宇 → 合体不能`、
>    `品》→ 精霊`、`恰缔 → 不明`。**"乱码汉字"永远可以这样还原**。
>
>    该块前面 `0x9220` 起是 u32 偏移指针表（`0x20/0x2E/0x42/0x56/0x6A/0x74/
>    0x84/0x8E`，基址 `0x9220`），等长原地注入不影响它。译文避开了越界字：
>    「阶」=`0x74E` 超过 `0x567`，改用「级」=`0x280`。

> **安度西亚斯战后罐子卡死（2026-08-03）**：即时存档显示 CPU 最终跳到低内存
> `0x00001008` 的数据区执行，并触发 Data Bus Error；可执行代码和既有 DMA/越界
> 防护均完好。对应文本资源 `F0016 0x5E0C4` 的原版第一串固定在解压块 `+0x18`，
> 中文“＞有一个罐子。”编码比原槽多 2 字节，固定布局构建器曾把它外移到 `+0x102`
> 并仅更新指针表；该事件却直接读取 `+0x18`，于是把指针表当字码连续绘制并写坏 RAM。
> 现缩为“＞有个罐子。”，并把该资源列入严格固定布局清单，构建期禁止任何字符串外移。
>
> **MARKER 类别绿框与 OTHER 慢速（test80 待实机确认）**：五条类别说明
> `0xEF298–0xEF33B` 在数据表里标为 dynamic，实际却由 F14 绘制。其中
> “一般用途”的“途”=`0x708`，“首领房间”的“房”=`0x768`，
> “其他用途”的“他/途”=`0x56C/0x708`，均越过 F14 上限 `0x567`；
> OTHER 同时含两个越界字码，正好是最严重的分支。现仅给这五条使用 F14
> 上下文别名，不重排全局码表；别名由 180 增至 182。
>
漏掉注入的槽位不会报错——它们保留原版日文码，而那些码在重排后的字库里指向别的汉字，
于是屏幕上出现「差込口 → 乐禁两」这类乱码。

## 2. 一个字是怎么显示出来的

游戏有**三条互不相同的文字渲染路径**。绝大多数误判都源于把它们混为一谈。

| 路径 | 文本格式 | 字库 / 入口 | 用途 | 容量 |
|---|---|---|---|---|
| **F13 动态** | 2 字节小端字码，`FFFF` 结尾 | `F0013.BIN`；对话解码器 `0x8005C218`、legacy 菜单 `0x8004ACB8` | 剧情对话、动态菜单 | **0xACE = 2766** |
| **F14 静态** | 同上 | `F0014.BIN`；`0x800475FC` 一族 | 固定菜单、名字、技能、选项、物品名 | **0x567 = 1383** |
| **原版小字** | 有限 Shift-JIS 字节串 | `F0012.BIN` 图集；`0x80046D08` | 原版假名、部分系统 UI | 只有原版准备好的那些字 |

正文**不是 Shift-JIS**：是一串 2 字节小端字码，控制符同样 2 字节且高字节为 `FF`
（`01FF`=▽、`03FF`=换行…完整表见 `src/text_codec.py`）。所以码表、字库、文本必须同步生成。

### F14 的 1383 格是硬墙

F14 是 208×252 的 4bpp 四平面纹理，12×12 格，每平面 346 格 → `346×4−1 = 1383`。
**这个数字改不了**（加宽会让纹理压缩后超出 F0014.BIN 固定的 24576 字节；而文件不能移动，
因为 `FILEPOS.DAT` 要求全盘文件连续且 LBA 单调递增）。完整论证见
`archive/docs/F14_CAPACITY_RE.md`。

**症状识别**：某屏文字**空白 / 黑块 / 彩色方块**，几乎总是 F14 字码越界
（U/V 表按 `容量×4` 分配，越界会读到堆里别的数据，于是从 VRAM 随机位置取图）。

### 破墙的办法：F14 上下文别名

原命名键盘占用了 204 个低码位。关键反转是：**这 1383 个物理格不必都有全局唯一含义。**
对**确认只走 F14** 的记录（交涉选项、技能名、预设人名），编码时改用「上下文专用低码别名」，
F14 对应物理格改画中文字：

- 普通对话仍用正常 F13 字码；
- 这些记录在自己的上下文里用低码别名；
- 名字则由 `0x8004AD6C` 的**混合渲染器**分流——全部字码属于原命名字符集就走小字路径
  （保住日文键盘输入的名字），出现任意非命名码就走 F14。只有确认属于姓名的入口才可
  改到该 wrapper。此前推断共享的类型 6 列表调用 `0x8006D9E4` 必须保留原版小字
  渲染器，但 test60 已证伪“它是唯一破坏者”：恢复后 MARKER 仍以同类地址越界卡死。
  test60 已证明它不是唯一破坏者；test62 随后定位到真正问题是 MARKER
  类型 6 F14 行跨度不足。test64 保留 hybrid 路由，并在公共构造器修正容量。

实现见 `src/f14_context_aliases.py`，当前 180 个别名覆盖 658 个上下文字符。

## 3. 三层「不能移动」

游戏并不总是通过指针表读数据。这解释了「指针表看着完全正确却仍然卡死」：

1. **光盘文件**不能变长或移位 —— LBA / FILEPOS.DAT / ISO 目录必须一致。
2. **文件内资源**不能移位 —— 部分代码按**固定文件偏移**读资源。
3. **资源内字符串**不能移位 —— 部分菜单直接读解压缓冲里的**固定偏移**。

对应的注入策略（`src/text_resource_builder.py` / `text_file_builder.py`）：

- **exact-size**：每个被替换资源保持原偏移 + 原声明大小；
- **固定布局**：装得下的译文写回原槽；普通块一旦超槽就整体紧凑重排；
- **allow-growth**：仅 F0017/F0094 四个明确的固定偏移查表块可把超槽串追加到尾部；
- **INPLACE**：既要固定内部布局又要等文件大小的资源（F0018 0x1F5C、F0040 四块）。

当前构建共 751 块：745 个参与资源构建（489 固定布局、256 紧凑重排），另有
5 个 passthrough 和 1 个静态块。全盘审计发现 61 个“单条外移会导致指针逆序”
的候选块，其中 57 个按对话策略紧凑重排，4 个按明确白名单 allow-growth。

```powershell
python -m tools.audit_text_resource_layout --summary `
  --json build\text_resource_layout_audit.json
```

> ⚠️ 已确认按固定偏移读取的菜单块（F0076 0x2C7C、F0084 0x800/0xE000、F0075 block0）
> **必须继续使用短译文**，禁止把字符串搬到缓冲末尾。

## 5. 常见工作流

完整的新手学习路线见 [`PS1_TEXT_WORKFLOW.md`](PS1_TEXT_WORKFLOW.md)，包括 PS1 RAM、
MIPS 延迟槽、三套字库、GPU DMA 链，以及从漏翻到测试镜像的完整操作。

**定位漏翻**（在 `new/` 中运行）：

```powershell
python tools/locate_text.py "屏幕上的连续几个字"
python tools/locate_text.py todo --dataset overlay
python tools/locate_text.py stats
```

它会同时搜索 `text.json`、`slpm_text.json`、`overlay_text.json` 和
`f0098_text.json`，报告应编辑的文件、记录 ID、资源文件及偏移。工具只读，不会修改数据。

**改译文** → 改 `text.json` → 若用字集合变了跑 `python tools/rearrange_codetable.py`
→ `--dry-run` → 完整构建。

**加缺字** → `src/codetable.py` 的 `NEW_CODETABLE_ENTRIES` + `codetable.json` 末尾追加
（连续编号）→ 重排 → 构建。字模从 `P:\ROMHacking\fusion-pixel-12px.otf` 渲染。

**诊断显示错误**：
1. `python tools/textscan.py rev "错字"` 反查字码；
2. 字码 ≥ 0x567 且出现在静态画面 ⇒ F14 越界，考虑加上下文别名；
3. 错字**每次固定** ⇒ 码位/表问题；**随机变化** ⇒ 才考虑缓存/时序；
4. 必要时用 DuckStation 存同帧 RAM+VRAM 离线分析。

⚠️ **校验注入结果必须用构建的最终码表**（`plan.global_character_overrides` +
`plan.font_overrides`），不能用磁盘上的 `codetable.json` —— 构建会在内存里重映射部分字码，
用旧表解码会把正常字误报成乱码。

## 7. 光盘注入

raw BIN 2352 字节/扇区，Mode2 Form1，用户数据偏移 24、长 2048。`src/disc_injector.py`
按 manifest 原位替换（**长度必须一致**）→ 重建 EDC 与 ECC P/Q → 回读逐字节比对。
无需外部修复工具。

> **EDC/ECC 正确 ≠ 扇区可读。** PS1 光驱按 XA 子头的 submode 过滤扇区：正常数据扇区
> `0x08`、文件末扇区 `0x89`、空白扇区 `0x00`。没有 Data 位的扇区永远读不回来（表现为黑屏）。
> 相关知识保存在 `archive/src/disc_relocation.py`（未启用）。

## 9. 硬规则

1. 永远从 `Game/ogd/` 和 `extrac/` 的干净原版构建，**不在旧补丁产物上二次打补丁**。
2. 改码表后必须**全量重建**字库、文本、SLPM、overlay。
3. 某字在 F13 正常**不代表**在 F14 可用；先查 `< 0x567` 和真实字模。
4. **「能编码成 Shift-JIS」不等于「小字渲染器能显示」**——它只有原版准备好的那些字。
5. 不要只看资源内部指针表；外部代码可能按固定文件偏移或解压偏移读取。
6. 不要扩大或移动 F0014，除非重新证明 FILEPOS、ISO、XA 子头和全部硬编码 LBA。
7. MIPS `jal` 的**延迟槽属于调用的一部分**；换渲染器时必须核对寄存器**和栈参数**
   （只改 `jal` 会因为绘制缓冲栈槽不同而破坏内存）。
8. 任何原位补丁都**先校验原字节**，不符立即失败，不要「尽量写进去」。
9. 测试码表变更必须**冷启动 + 新游戏**：旧存档里的名字是按旧码表编码的。
10. 症状是**确定性**的就不是竞态——别再往缓存/时序方向查。
